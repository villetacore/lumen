# Инструкции по разработке Lumen

Lumen развивается в AI-центр управления студией: проекты, знания, сервисы,
агенты, рабочие сценарии и проверяемые результаты. Это направление продукта;
конкретные новые функции пока описаны как план, не как готовая реализация.

## Начало работы

Прочитай `docs/plans/PRODUCT_DIRECTION.md`, `docs/plans/IMPLEMENTATION_GUIDE.md`,
`docs/plans/BACKLOG.md` и `docs/plans/PROGRESS.md`, затем код относящейся области.
Для runtime читай `docs/plans/AGENT_RUNTIME.md`. Учитывай текущий запрос владельца:
запрос на планирование не является командой начинать реализацию.

Перед изменениями проверь git status/diff, сохраняй существующую работу.
Не считай документацию доказательством, что функция реализована. Старые M0–M4
в `docs/ROADMAP.md` — исторический план; порядок новой реализации задают срезы
A–G в IMPLEMENTATION_GUIDE и зависимости LUM-задач.

## Ограничения текущего этапа

- Рабочая область: Go backend `server/`, React/TypeScript `web/`, документация
  и необходимая серверная инфраструктура. Не изменяй `desktop/` (Flutter/Rust)
  без отдельного запроса владельца; сохраняй совместимость существующего API.
- Развивай существующий модульный монолит. Не переписывай стек, не делай fork
  OpenClaw, не добавляй микросервисы или инфраструктуру без задачи/обоснования.
- Markdown — оригинал локального контента; сервис-источник владеет внешними
  объектами. Операционные данные и поисковые проекции различаются по восстановлению.
- HTTP, MCP, агенты и автоматизации используют общие service/policy/actions.
  Доступ определяется кодом, не системным промптом или ролью агента.
- Агентный runtime строится отдельно от RAG. OpenSearch не обязателен для первого
  агентного сценария. Не включай shell/code execution в `lumend` ради демо.
- Не включай реальные внешние записи, отправку сообщений, deploy или доступ к
  боевым данным только на основании задачи разработки; используй тестовые адаптеры.
- Не изменяй принятый ADR молча: документируй уточнение и миграцию.

## Выполнение и проверка

Выбирай небольшую задачу с выполненными зависимостями. Реализуй полный указанный
сценарий, не расширяя его массовым refactor. Обновляй PROGRESS с фактами выполнения.
Для новой записи/очереди проверь повтор, конфликт и рестарт; для доступа — запрет
чужих данных; для UI-редактирования — сохранность draft.

Существующие команды: `go test ./...` в `server/`; `npm run typecheck` и
`npm run build` в `web/`. Дополнительные tests — по изменению. Общий `make test`
включает desktop, поэтому для текущего этапа используй целевые команды.
При изменении только документов проверяй ссылки и diff, тесты приложения не нужны.

Не отмечай `done`, если приёмка не пройдена; запиши blocker или partial.
В итоговом отчёте укажи изменённое поведение, проверки, ограничения и следующий ID.
Не запускай реализацию всего backlog без соответствующего задания.
