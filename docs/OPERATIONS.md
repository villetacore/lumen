# Эксплуатация и восстановление

## До первого запуска

Запускайте один экземпляр `lumend` на vault. Для Kubernetes используйте одну
реплику, стратегию `Recreate` и постоянный том `/vault`. Пользователь стандартного
контейнера — UID 65532; у него должны быть права записи на том.

Для сетевого доступа настройте HTTPS, `LUMEN_PUBLIC_URL` и токен или OIDC.
Без этих настроек API может быть открыт: смена адреса на `0.0.0.0` сама по себе
не включает защиту. Вошедшие пользователи имеют доступ ко всему vault.

Конфигурация: [параметры сервера](../server/README.md), [OIDC](AUTH.md),
[секреты](SECRETS.md). Контейнер и CI: [DEPLOY.md](DEPLOY.md).

## Что сохранять

Резервная копия должна включать **весь vault, в том числе скрытую `.lumen/`**:
заметки, конфигурацию подключений, состояние импорта, корзину, резервные копии
импорта и, при шифровании, `crypt.json`. Отдельно сохраните конфигурацию запуска
и возможность восстановить ссылки на секреты. Не публикуйте эти копии в git.

Для зашифрованного vault нужны и ключевой файл, и парольная фраза. Без них
копии шифротекста недостаточно. Сами секреты храните отдельно от backup.

## Согласованная копия

1. Остановите `lumend` и остальные процессы, записывающие в vault.
2. Сделайте snapshot тома или архив всей папки, сохранив скрытые файлы.
3. Убедитесь, что архив читается; храните копию вне исходного диска.
4. Запустите сервис и проверьте `/healthz`.

Например, для остановленного сервера с vault `/srv/lumen/vault`:

```bash
tar -czf lumen-vault-backup.tar.gz -C /srv/lumen vault
tar -tzf lumen-vault-backup.tar.gz > /dev/null
```

Для Docker сначала `docker stop lumen`, затем копируйте или снимайте snapshot
именованного тома средствами своего хоста. Не удаляйте том при обновлении.
Проверка списка архива подтверждает читаемость, но не заменяет тест восстановления.

## Проверка восстановления

Распакуйте копию **в новую пустую папку**, не поверх действующего vault. Сохраните
оригинал до проверки. На изолированной копии отключите внешние подключения
(сохраните конфиг, выставьте `enabled: false` у элементов `integrations` в
`.lumen/integrations.yaml`) и не подключайте реальные секреты интеграций.

Запустите ту же версию `lumend` на свободном локальном порту:

```bash
./dist/lumend --vault /path/to/restored/vault --addr 127.0.0.1:8788
curl -fsS http://127.0.0.1:8788/healthz
```

Для зашифрованной копии дополнительно настройте источник парольной фразы.
Проверьте число и содержимое заметок, задачи, связи проекта и чтение
зашифрованных файлов. Только после этого переключайте рабочий сервис.
Внешний календарь восстановится после включения подключений и доступности
источников; offline snapshot событий пока отсутствует.

## Обновление и откат

Перед обновлением сохраните текущий тег образа/версию бинарника, конфигурацию и
backup vault. Используйте неизменяемый тег `<sha12>`, а не `main`, если нужно
точно знать запущенную версию. Остановите прежний процесс перед запуском нового.

После обновления проверьте `/healthz`, загрузку UI, вход, открытие существующей
заметки и состояние подключений. Health endpoint не проверяет доступность всех
внешних сервисов и успешность входа OIDC.

Для отката верните предыдущий тег образа или бинарник. Если обновление меняло
формат данных, следуйте его инструкции миграции: откат бинарника не отменяет
изменения vault. Восстанавливайте backup только при остановленных писателях,
понимая, что записи после момента копирования будут отсутствовать.

В поставке через GitOps тег возвращается изменением репозитория инфраструктуры;
ручной `kubectl set image` будет перезаписан Argo CD. Сам открытый репозиторий
не содержит закрытых настроек кластера.
