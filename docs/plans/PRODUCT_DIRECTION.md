# Направление продукта: AI-центр управления студией

Дата: 2026-10-14. Направление уточнено по запросу владельца; архитектурные детали
ниже — предлагаемый способ реализации. Конкретные сервисы и тип студии пока неизвестны.

## Продуктовое обещание

**Lumen связывает людей, проекты, знания и сервисы студии, чтобы поручение
превращалось в проверяемый результат с помощью AI-агентов.**

Основная единица работы — поручение в контексте проекта: «подготовь сводку»,
«собери материалы», «разбери блокеры», «подготовь изменение». Пользователь видит
источники, ход выполнения, результат и изменения в сервисах. Чат — один из
интерфейсов поручения; рядом существуют карточка проекта, документы и очередь работ.

Главный показатель пользы — сколько реальных поручений завершено с пригодным
результатом и сколько ручных переходов/операций устранено. Количество агентов,
коннекторов и сообщений само по себе не является результатом.

## Как использовать ориентир OpenClaw

OpenClaw описывает gateway как центральную точку подключения клиентов и управления
агентами: [архитектура](https://docs.openclaw.ai/concepts/architecture).
Полезный образец для Lumen — отдельный жизненный цикл запуска, контекст и вызовы
инструментов: [agent loop](https://docs.openclaw.ai/concepts/agent-loop).
Регулярные запуски также должны быть полноценными заданиями со своим результатом:
[automations](https://docs.openclaw.ai/automation/cron-jobs).

Это архитектурный ориентир, а не требование совместимости или копирования реализации.
Проверены официальные материалы 2026-10-14; перенос конкретных функций потребует
отдельной проверки версии, API и лицензии.

| Что взять как принцип | Как применить в Lumen |
|---|---|
| Постоянно работающий сервер управления | Существующий `lumend` принимает поручения, события и расписания |
| Сессии и запуски агентов | Сессия принадлежит пользователю/проекту, каждый run имеет результат и статус |
| Tools и переиспользуемые инструкции | Версионируемые сценарии студии с ограниченным набором возможностей |
| Память и контекст | Разделить историю сессии, проверенные знания проекта и пользовательские предпочтения |
| Автоматизации | Сводки и проверки по расписанию/событию, с дедупликацией и журналом |
| Каналы общения | Сначала web, затем один реально используемый студией канал |

Предлагаемый выбор: развивать существующий Go/React Lumen самостоятельно; не делать
fork OpenClaw и не вводить зависимость от его runtime в первом релизе. Это сохраняет
файловые знания, текущие API и контроль над студийными сценариями. Адаптер стороннего
runtime допустим позже, если он заметно дешевле собственного решения по конкретной
задаче; решения о нём фиксируются ADR, а не скрываются внутри интеграции.

## Отличительные возможности для студии

| Возможность | Ценность | Этап |
|---|---|---|
| Контекст проекта | Краткое описание, ответственные, ссылки на сервисы, решения и материалы в одном месте | Первый продуктовый срез |
| Поручения агенту | Запуск с целью, источниками и ожидаемым результатом; видно, что сделано | Первый продуктовый срез |
| Результаты как артефакты | Сводка, план, документ или diff сохраняются с происхождением и версиями | Первый продуктовый срез |
| Сценарии студии | Повторяемые процедуры: сводка проекта, подготовка встречи, проверка готовности выпуска | Первый продуктовый срез |
| Очередь решений | Что требует человека: конфликт, подтверждение, недостаток данных | Первый продуктовый срез |
| Знания с цитатами | Ответы на основе регламентов и проектных документов | Полный пилот |
| Расписания и события | Сводка утром, проверка блокеров, подготовка отчёта при смене этапа | Полный пилот |
| Изоляция проектов/клиентов | Агент и сотрудник получают только разрешённый контекст | До работы команды на реальных данных |
| Подготовка клиентских материалов | Черновики отчётов/предложений из утверждённых источников | После пилота, если нужно студии |
| Поручения на код | Подготовленный diff/PR в изолированном checkout, проверки и review | Отдельная последующая возможность |
| Несколько специалистов | Явное распределение частей задачи с общим budget и сборкой результата | После доказанной пользы одного агента |

«Поручения на код» внутри продукта и AI-разработчик, который сейчас будет строить
сам Lumen, — разные вещи. Подготовка инструкций для разработчика не включает
запуск shell-инструментов для агентов будущего продукта.

## Первый демонстрируемый результат

Один владелец создаёт проект, связывает заметку и тестовое подключение трекера,
выбирает сценарий «Сводка проекта» и запускает его. Один агент читает разрешённые
задачи и документы, сохраняет сводку с источниками и показывает блокеры. Владелец
может продолжить сессию и запросить поддерживаемое действие над конкретным issue;
система показывает preview, выполняет подтверждённое действие и фиксирует результат.

Если трекер/провайдер ещё не выбран, тот же сценарий работает на явно обозначенном
demo adapter и детерминированном fake model в тестах. Это не считается готовой
боевой интеграцией. Демонстрация не требует vector search, внешнего мессенджера,
нескольких агентов или доступа к терминалу.

## Граница первого полного пилота

Один сервер, одна студия/workspace, web, один LLM provider, один реальный трекер,
vault + один внешний источник документации, один агент с несколькими профилями,
два сценария («Сводка проекта», «Подготовка встречи»), расписание сводки, MCP server
для чтения и подтверждаемое внешнее действие. Несколько сотрудников включаются
после тестов ролей и изоляции проектов. Клиентский портал пока не строим.

Не включать в этот релиз универсальный конструктор workflow, маркетплейс skills,
полную ERP/CRM/бухгалтерию, визуальный редактор оргструктуры агентов, массовую
автономную запись во все сервисы, собственную инфраструктуру обучения моделей.
Из дополнительных идей брать те, что используют общее ядро и сокращают ручную
работу в выбранном сценарии.

## Условия успеха

- Поручение имеет устойчивый статус и результат после обновления страницы/рестарта.
- Сводка содержит проверяемые ссылки и различает факт, вывод и неизвестное.
- Рабочий сценарий проходит без ручного копирования данных между сервисами.
- Ограничения прав одинаковы для человека, агента, расписания и MCP.
- Пользователь понимает цену/лимит запуска и может остановить дальнейшую работу.
- По крайней мере два сотрудника с разными правами проходят изоляционные тесты
  до включения командного режима, даже если пилот начинается с владельца.

Перед расширением записать baseline времени ручного выполнения двух сценариев,
долю принятых результатов, число исправлений и стоимость runs. Цели улучшения
согласовать по этому baseline; текущие цифры пользы пока не измерены.
