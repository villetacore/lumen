# AI, MCP и поиск по знаниям

Статус: проектирование. Здесь RAG означает поиск фрагментов документов для ответа
модели; это не обучение модели на базе и не обязательный выбор одной vector DB.

После уточнения направления OpenClaw/студия исполнение поручений вынесено в
[AGENT_RUNTIME.md](AGENT_RUNTIME.md). Базовый агент запускается до полного RAG:
читает разрешённые данные через обычные API/лексический поиск и сохраняет
артефакты. Этот документ определяет последующее расширение поиска и MCP.

## Разделение задач

| Компонент | Ответственность |
|---|---|
| Search | Находит документы/фрагменты и фильтрует доступ |
| RAG | Собирает ограниченный контекст, вызывает модель, связывает ответ с источниками |
| Assistant | Ведёт диалог, выбирает чтение и готовит разрешённые действия |
| MCP server Lumen | Даёт внешнему AI-клиенту контролируемый доступ к Lumen |
| MCP client Lumen | Подключает одобренные инструменты других систем |
| Action service | Проверяет и выполняет действия независимо от того, кто их предложил |

MCP не заменяет очередь интеграций, поисковый индекс или API трекера. Для массовой
синхронизации предпочтительны адаптеры API с курсорами и webhook. Для интерактивных
инструментов можно использовать MCP с теми же правилами доступа.

## Выбор поискового хранилища

| Вариант | Когда применять | Компромисс |
|---|---|---|
| SQLite FTS5 | Базовый личный запуск и первый полнотекстовый поиск | Семантическую часть нужно реализовывать отдельно |
| OpenSearch | Серверная база знаний: лексический + векторный поиск, фильтры | Отдельный сервис, ресурсы, обновления и эксплуатация |
| PostgreSQL + pgvector | Если PostgreSQL уже нужен операционной системе | Совмещение SQL и векторов; качество гибридного поиска и фильтров проверяется отдельно |

Рекомендация для пилота: FTS5 как базовый режим, OpenSearch как первый кандидат
для RAG. Если в реальном окружении уже есть PostgreSQL и нет OpenSearch, сравнить
pgvector на том же корпусе перед добавлением нового сервиса. Не внедрять оба
векторных backend одновременно. OpenSearch поддерживает объединение лексического
и семантического поиска: [официальная документация](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/).
Возможности и ограничения pgvector: [документация проекта](https://github.com/pgvector/pgvector).

До выбора измерить: объём и языки документов, p95 поиска, RAM/диск, время полной
индексации, качество top-k, удаление и ограничения ACL. Отдельного этапа закупки
или развёртывания кластера этот документ не запускает.

## Индексация

`источник → нормализация → версия/ACL → chunks → embeddings → поисковая проекция`.

Начать с Markdown vault и одного внешнего источника документации. PDF, OCR,
архивы и медиа — после проверки текстового пути и лимитов обработки.

Для документа хранить `document_id`, `workspace_id`, `connection_id`, `source_id`,
`source_url`, `source_revision`, `content_hash`, `updated_at`, `fetched_at`,
`acl_version`, `visibility`, `deleted_at`, `parser_version`.
Для chunk: ID документа, heading path, anchor/диапазон строк, текст, порядковый
номер, hash, embedding model/version/dimension и версия схемы индекса.

Разбиение по заголовкам и смысловым блокам; не разрывать без необходимости
код/таблицы. Размер и overlap подбирать на eval-корпусе. Обновление документа
атомарно переключает активную версию chunks; старые части удаляются, чтобы они
не смешивались с новой редакцией. Embedding пересчитывать только при изменении
текста/модели. При смене размерности — новый индекс и переключение alias после
проверки полноты; откат сохраняет совместимую версию.

Удаление и отзыв прав должны инвалидировать выдачу, answer cache и доступ к
истории ответов. До физического удаления chunks служит deny/tombstone в
авторитетном policy store. Сбой обновления ACL не расширяет доступ. Доступность
недавних изменений отображается через состояние индексации.

## Путь запроса

1. Определить пользователя, workspace, разрешённые источники и права.
2. Выполнить лексический и векторный поиск с ограничениями доступа внутри каждой
   ветки. Не получать глобальные результаты, чтобы потом убрать их только из UI.
3. Объединить и дедуплицировать кандидатов, при необходимости rerank. Перед
   передачей текста reranker и LLM повторно проверить актуальные права кандидатов.
4. Собрать контекст с лимитом tokens, исключить устаревшие/удалённые версии.
5. Сформировать ответ с источниками: документ, ссылка, фрагмент и версия/время.
   Если источников недостаточно, явно сообщить это; не придумывать подтверждение.

Механизм фильтрации вектора зависит от движка и настроек; выбрать его вместе с
backend и проверить на изоляционных тестах, см. [OpenSearch filtering](https://docs.opensearch.org/latest/vector-search/filter-search-knn/index/).
При недоступности semantic search разрешён явный fallback к разрешённому
лексическому поиску. Нельзя использовать общий неотфильтрованный индекс как fallback.

Права проверяются и на цитаты, и на выдачу истории диалога; кэш включает пользователя/
группы, workspace, ACL version и версии документов. При отзыве доступа ранее
сохранённый ответ с защищённым содержимым скрывается/инвалидируется. Уже прочитанное
или скопированное человеком содержимое технически отозвать невозможно.

## Провайдеры моделей

Ввести независимые интерфейсы `ChatModel`, `EmbeddingModel` и опциональный
`Reranker`. Первый релиз поддерживает один выбранный локальный либо удалённый
провайдер за адаптером. Для каждого — endpoint, model ID, secret reference,
таймауты, лимиты контекста, concurrency, token/cost budget, streaming/cancellation.
Совместимость с конкретным API и tool calling подтверждается contract tests.

Политика задаёт, какие источники можно отправлять удалённому провайдеру; по
умолчанию закрытая база не экспортируется автоматически. Облачный fallback для
локальной модели не включать без отдельной настройки владельца. Embeddings тоже
передают содержимое провайдеру и требуют этой политики.

Шифрование vault не защищает открытые chunks и embeddings в другом хранилище.
Поисковый backend, БД и бэкапы должны защищаться отдельно; не записывать туда
значения паролей. Серверный RAG требует доступа к расшифрованному тексту и несовместим
с моделью «сервер никогда не видит содержимое» без переноса retrieval на клиент.

## MCP server

Первый набор только для чтения: `search_knowledge`, `get_document`, `list_tasks`,
`get_project_context`, `get_integration_status`. Resources дают разрешённые
документы и инструкции; prompts — удобные шаблоны, не механизм прав.

Потом добавить `prepare_action` и чтение статуса. Исполнение требует подтверждения,
записанного доверенным интерфейсом либо заранее заданной узкой политикой. Флаг
`approved=true` из аргументов модели не считается разрешением.

Для удалённого доступа — Streamable HTTP, для локального при необходимости stdio.
Существующий SSE `/api/v1/events` не является MCP endpoint. Перед реализацией
зафиксировать опубликованную версию протокола и совместимую Go-библиотеку, покрыть
initialize, capability negotiation, схемы, ошибки, отмену и лимиты integration tests.
Не считать draft спецификации стабильным контрактом.

Для HTTP проверить OAuth discovery, audience/resource binding, scopes и срок
токена. Существующий вход через Keycloak не гарантирует готовую совместимость
с MCP-клиентами; нужен отдельный сценарий настройки и тест. Основы:
[MCP authorization, версия 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).
Это версия справочного источника, не утверждение о последней версии протокола.

## MCP client и инструменты

Подключения устанавливает администратор: фиксированные серверы, способы auth,
допустимые tools и их схемы, scopes, таймауты и лимит размера результата.
Discovery не даёт автоматического права исполнить всё найденное. Изменение схемы
инструмента требует пересмотра разрешения. По умолчанию — чтение.

Не передавать входящий токен Lumen в другой сервис. Внешние credentials разделять
по подключению и пользователю. Не разрешать модели подключать произвольный URL
или запускать stdio-процесс из полученной команды. Учесть рекомендации
[MCP security](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).

Текст документов и результаты tools — недоверенные данные. Инструкции внутри них
не меняют policy, список tools и адресатов передачи данных. Ограничить число
шагов агента, время, tokens и обращения к сервисам; дать пользователю остановку.
Остановка генерации не отменяет уже подтверждённое внешнее действие.

## Качество и выпуск

Подготовить минимум 50 реальных вопросов: русский/английский, точные ID, смысловые
запросы, противоречащие и отсутствующие документы, разные группы доступа.
Для каждого указать ожидаемые источники и допустимый ответ/отказ.

Предварительные цели пилота (не измеренные показатели): Recall@10 ≥ 0,85 для
вопросов с известным ответом; ≥ 90% проверенных фактических утверждений подтверждены
цитатой; ноль выдач недоступного текста в тестах изоляции. Измерять retrieval p50/p95,
время первого токена, стоимость/запрос и задержку обновления индекса на описанном
оборудовании. Численные latency-SLO установить после baseline, не угадывать.

Проверить prompt injection, отзыв доступа в процессе генерации, stale chunks,
сбой модели, исчезновение индекса, таймаут внешнего tool, подмену аргументов после
approval и неизвестный исход действия. RAG-функции не выпускаются раньше прохождения
этих проверок и рабочего поиска без модели. Для раннего агента без RAG обязательны
проверки policy, tools, budgets, cancellation и восстановления из AGENT_RUNTIME.
