# Lumen: AI-центр управления студией

Дата: 2026-10-14. Статус: **предложение к реализации**, а не описание готовых функций.
Область работ: `server/`, `web/`, серверная инфраструктура и документация.
Flutter и Rust-клиент пока не меняем; совместимость существующего API сохраняем.

## Цель

Lumen становится рабочей средой студии: поручения AI-агентам в контексте проектов,
общие знания, действия в существующих сервисах и повторяемые рабочие сценарии.
Результаты сохраняются как документы и другие артефакты с источниками и историей.
Сами сервисы продолжают отвечать за свои данные и бизнес-правила.

Уточнение владельца: ориентир — OpenClaw с возможностями для своей студии.
[Продуктовое направление](PRODUCT_DIRECTION.md) определяет, что именно строим;
[инструкция реализации](IMPLEMENTATION_GUIDE.md) задаёт порядок для кодирующего
агента. Наличие новых планов не означает, что агентные функции уже работают.

Примеры законченных сценариев:

1. Открыть проект и увидеть его заметки, issues, встречи и связанные сервисы.
2. Найти инструкцию по развёртыванию одновременно в vault и подключённой документации;
   увидеть источник, дату обновления и доступность оригинала.
3. Закрыть issue из Lumen: увидеть точное изменение, отправить его в сервис,
   получить подтверждение и обновить карточку без дублирующей операции.
4. Спросить помощника «что мешает выпуску проекта?» и получить ответ со ссылками
   на доступные пользователю задачи и документы. По запросу подготовить действие.
5. Подключить внешний AI-клиент к MCP Lumen; использовать те же права и поиск,
   что и в веб-интерфейсе.
6. Запустить сценарий «Сводка проекта», получить сохранённый отчёт с блокерами
   и источниками, затем настроить его повторение по расписанию.

Слово «riak» в запросе интерпретировано как **RAG** — извлечение документов для
ответа модели. Riak как конкретная БД в этот план не включён. Список реально
развёрнутых сервисов, объёмы документов и требования к размещению моделей пока
неизвестны; наличие коннектора в коде не доказывает наличие сервиса в окружении.

## Что установлено по репозиторию

Это обзор исходников, не результат запуска приложения или полного аудита безопасности.

| Область | Фактическая основа | Что мешает следующему этапу |
|---|---|---|
| Backend | Go, `net/http`, слои domain/service/adapters, встроенный UI | Нет устойчивого журнала действий и общей политики доступа к объектам |
| Хранение | Markdown, lossless-правки, шифрование через `vault.Codec` | `main.go` создаёт `index.NewMemory`; ревизии и поисковый индекс в памяти |
| Поиск | `Memory.Search` ищет подстроки в заголовке, пути и строках | Нет полнотекстового/семантического поиска и выдачи по правам источника |
| Интеграции | ICS, CalDAV, Nextcloud Notes, GitHub/Gitea; реестр и scheduler | В основном импорт; нет общего контракта внешних действий, webhook inbox/outbox |
| Импорт заметок | `refreshNote` обновляет source-маркеры и статус задачи | Изменённый текст внешней заметки не обновляется, хотя `source_hash` меняется |
| Надёжность импорта | Курсоры пишутся в JSON; события календаря живут в индексе | Курсор может сохраниться после ошибки применения; после рестарта условный 304 не восстановит потерянные события |
| Идентичность | `NoteBySource(integrationID, externalID)` | `taskBlockID` зависит только от external ID: нужно проверить коллизии разных подключений |
| Web | React/TS, Query, Router, SSE | Инвалидация всех запросов; редактор сбрасывает draft при новой revision |
| Вход | OIDC/Keycloak, роли, token mode | Вход в приложение ещё не означает разграничение документов и действий разных пользователей |
| AI / MCP | В исследованных `server/` и `web/` реализации не обнаружены | Нужны отдельные контракты поиска, моделей, инструментов и разрешений |
| Документация | Подробные основы и ADR | Местами смешаны реализованное и проектируемое: SQLite, sync, CodeMirror, Zustand, WS |

## Рекомендуемое направление

- Сохранить Go и React, развивать модульный монолит с общими use cases для HTTP,
  MCP и фоновых заданий. Делить на микросервисы сейчас нет основания.
- Сохранить Markdown как оригинал локальных знаний. Внешние объекты принадлежат
  исходным сервисам. Поисковые индексы — производные данные.
- Добавить отдельное устойчивое операционное хранилище: SQLite на первом этапе
  для одного экземпляра сервера. Оно содержит jobs, действия, права и связи;
  его нельзя считать удаляемым поисковым кэшем.
- Подключать существующие API сервисов через адаптеры. MCP использовать для
  взаимодействия с AI-клиентами и доступа к одобренным внешним инструментам.
- Сначала сделать надёжными импорт, права и один полный сценарий действия;
  затем запустить одного агента с обычным поиском/API и артефактами. RAG и MCP
  расширяют это ядро, не задерживая первую полезную агентную функцию.
- OpenSearch рассматривать как серверный поисковый backend. Включать его после
  проверки на реальном корпусе; базовый запуск Lumen не должен требовать кластера.

## Последовательность поставки

S0–S4 ниже группируют технические направления. Активный порядок поставки — срезы
A–G из [инструкции реализации](IMPLEMENTATION_GUIDE.md): базовый агент появляется
после ядра/интеграций и **до полного RAG**, затем добавляются сценарии студии.

| Этап | Проверяемый результат |
|---|---|
| S0: основания | Инвентаризация сервисов, устранение рисков потери draft/импорта, текущий API описан честно |
| S1: надёжное ядро | Устойчивые данные и задания, права, контракт API, диагностика и восстановление |
| S2: единая точка | Карточка проекта + подключённые источники + одно действие в существующем сервисе |
| Studio: агентное ядро | Устойчивый run, артефакты, два сценария, память и расписание |
| S3: знания | Поиск и RAG с источниками, удалениями, контролем доступа и измеренным качеством |
| S4: AI-интерфейс | MCP server, помощник и ограниченное подключение внешних MCP-инструментов |

До оценки сроков нужен S0: неизвестны количество пользователей, объёмы, реальные
сервисы и доступные ресурсы. После S0 оценивать небольшие задачи, а не обещать
срок реализации всей платформы. Несколько пользователей допускаются только
после проверки изоляции; первый пилот — один владелец и один сервер.

Отложено: переписывание Flutter, desktop sync, CRDT, браузерный offline vault,
универсальная платформа плагинов, собственный workflow-конструктор, Kubernetes,
автономные массовые изменения сервисов нейросетью.
