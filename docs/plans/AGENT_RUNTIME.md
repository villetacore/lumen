# Исполнение агентов и сценариев студии

Статус: предлагаемые контракты. Дополняет [архитектуру](ARCHITECTURE.md) и
[AI/MCP/RAG](AI_MCP_RAG.md). Это план runtime продукта, не инструкция AI-разработчику.

## Минимальное ядро

`вход → session → run → разрешённый контекст → model → tool/action → artifact`.
Модель предлагает следующий шаг; сервер определяет доступ, исполняет инструмент
и записывает результат. Знания и инструменты не зашиваются в конкретного провайдера.

| Сущность | Минимальные поля и правила |
|---|---|
| AgentProfile | ID/version, инструкции, model profile, разрешённые tool IDs, budgets; роль агента не выдаёт права пользователя |
| Session | ID, workspace/project, owner, visibility, сообщения; отдельная история для каждого контекста |
| Run | ID, session, инициатор, trigger, profile/version, status, deadline, budgets, checkpoint, timestamps |
| RunStep | sequence, type, tool/model call ID, input hash, status, usage, результат/ссылка на него |
| Artifact | ID/version, project, run, авторство, тип, URI, sources, ACL, review status |
| Playbook | ID/version, входная JSON schema, ожидаемый тип результата, инструкции, tools, критерии завершения |
| Automation | owner, project, playbook version, schedule/event, timezone, misfire policy, enabled, budget |
| MemoryEntry | scope, факт/предпочтение, источник, автор, revision, expires_at, ACL; не произвольный ответ модели |

Контент принятого документа/сводки можно сохранять в Markdown; run metadata,
receipts, сообщения и approvals — в операционном хранилище. Не превращать каждое
событие токена в файл vault. Загруженные материалы и ссылки проверяются на права
при чтении, а не только при создании сессии.

## Состояния и восстановление

Run: `queued → running → waiting_approval / waiting_input → running → succeeded`.
Терминальные состояния: `failed`, `cancelled`, `expired`; после потери worker —
`interrupted` до восстановления. Ошибка шага не обязательно завершает весь run,
но её нельзя скрывать под успешным ответом.

- В одной сессии на первом этапе выполняется один run. Следующее сообщение
  ставится в очередь или явно корректирует текущий запрос, а не создаёт гонку.
- Запись шага и его стабильный tool-call ID предшествуют внешнему действию.
  Повторное исполнение использует тот же action ID. При неопределённом исходе
  run ждёт reconciliation; LLM не повторяет отправку по своей инициативе.
- После рестарта продолжить с последнего завершённого шага. Незавершённую генерацию
  можно начать заново с учётом расходов; уже исполненный tool повторно не запускать.
- Cancel прекращает новые шаги/генерацию; уже отправленное действие может завершиться.
  Его итог остаётся виден. Deadline и лимиты проверяются сервером перед каждым шагом.
- Lease не даёт двум workers одновременно вести run. Утративший lease worker
  не может записать новый шаг: проверяется fencing/version token.
- В run сохраняются версии playbook/profile/policy, использованные при запуске;
  текущие права и отзыв доступа всё равно проверяются перед каждым чтением/действием.

Для первой реализации достаточно последовательного цикла и SQL-очереди. Без
рекурсивного spawning, распределённого графа агентов и саморедактирования политик.

## Инструменты и полномочия

Tool registry описывает ID/version, input/output schemas, read/write effect,
required permissions, timeout, ограничения результата и способ аудита. Разрешённый
набор — пересечение прав пользователя, project scope, profile, playbook и connection.
Никакой текст инструкций не расширяет это пересечение.

Чтение выполняется через существующие сервисы с policy. Запись идёт через общий
Action service. Разрешение на запуск сценария не означает разрешения отправить
сообщение клиенту, изменить репозиторий или удалить данные: такие эффекты должны
быть явно описаны и разрешены политикой/пользователем.

Playbook сначала хранится как проверяемая конфигурация/инструкции, без исполняемого
кода сторонних plugins. Инструкция сценария задаёт результат и шаги, но не
credentials. Изменение tools/эффектов — новая версия с пересмотром разрешения.

Пример «Сводка проекта»: вход `project_id, period`; tools `list_project_resources`,
`get_document`, `list_tasks`; выход `report` с разделами «сделано / блокеры /
следующие шаги / источники». Готовность: документ сохранён, источники проверены,
неизвестные сведения обозначены. Сохранение локального отчёта разрешается scope
сценария; отправка отчёта наружу является отдельным действием.

## Контекст, память и артефакты

Есть три независимых слоя: ограниченная история сессии, retrieval знаний и
подтверждённая память. Сжатая история — производная от сообщений, содержит их IDs
и может быть пересобрана. Она не становится утверждённым регламентом студии.

Память разделяется на личную, проектную и общестудийную. Между ними нет
автоматического переноса. Предложенные моделью факты получают статус candidate;
публикация в общую память требует проверяемого источника и разрешения. Удаление
источника/отзыв доступа инвалидирует производные memory/summary/cache.

Артефакт хранит provenance и различает draft/accepted/superseded. Сводка не
заменяет оригинальную документацию. Если она построена на закрытых данных, её
читатели ограничены доступом ко всем использованным источникам; сервер повторно
проверяет это при открытии. Перенос в более широкую область — явная редактура/
публикация, не автоматическое наследование project visibility.

## Проактивность

Запуск по расписанию и webhook проходит тот же путь, что ручной run. Automation
имеет владельца, scope, версию сценария и budget; disabled/revoked owner прекращает
новые запуски. Дедупликация по automation ID + scheduled slot/event ID.

Политики обязательны: timezone, поведение DST, overlap (на первом этапе skip),
пропущенные запуски (не догонять все подряд), retry limits, quiet hours. UI хранит
время в UTC и показывает в выбранной зоне. Результат сводки сохраняется в проект,
уведомление появляется при новом полезном результате/проблеме; одинаковые состояния
не создают бесконечный поток сообщений. Отправка в мессенджер настраивается отдельно.

## Интерфейс и API

Предлагаемые endpoints: `/api/v1/agents`, `/sessions`, `/sessions/{id}/messages`,
`/runs`, `/runs/{id}`, `/runs/{id}/cancel`, `/playbooks`, `/artifacts`, `/automations`.
Полные пути всех перечисленных ресурсов имеют префикс `/api/v1`.
Ранее предложенный `/assistant/runs` заменяется этим единым контрактом до реализации;
два независимых типа запусков не вводить.

Создание run возвращает `202 + run_id`. Список шагов и артефактов доступен через
API; SSE — только доставка событий с cursor/refetch. Показывать ход инструментов,
стоимость, ожидание решения и результат; не сохранять скрытые рассуждения модели
как требуемый журнал. Новый endpoint должен войти в OpenAPI до генерации клиента.

## Кодовые агенты и внешние runtime — позже

Когда студии понадобится поручать код самому Lumen, ввести отдельный executor:
изолированный checkout, лимиты файлов/сети/ресурсов, короткоживущие credentials,
патч + тесты + review. Merge/deploy не входят в разрешение создать патч.
Рабочая директория сама по себе не является sandbox. Shell не исполняется
внутри основного процесса `lumend`. Эта возможность не нужна для первого пилота
и не блокирует использование внешнего AI-разработчика для разработки Lumen.
