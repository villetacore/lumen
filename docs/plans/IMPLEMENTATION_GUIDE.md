# Передача проекта кодирующему агенту

Дата: 2026-10-14. Документ определяет порядок реализации, но сам не означает,
что задачи выполнены. Текущий статус фиксируется в [PROGRESS.md](PROGRESS.md).

## Что читать и чему следовать

1. Корневой [AGENTS.md](../../AGENTS.md) и текущий запрос владельца.
2. [Направление продукта](PRODUCT_DIRECTION.md): зачем строится Lumen.
3. [Архитектура](ARCHITECTURE.md), [agent runtime](AGENT_RUNTIME.md) и документ
   нужной области: [web](WEB.md), [интеграции](INTEGRATIONS.md), [AI](AI_MCP_RAG.md).
4. [Backlog](BACKLOG.md) и [progress](PROGRESS.md): ID, зависимости, приёмка.
5. Реальный код и существующие тесты; планы не являются доказательством реализации.

Новый продуктовый акцент и последовательность поставки в этом документе уточняют
ранние этапы S0–S4. IDs задач сохранены. Не переписывать планы заново при каждом
старте и не реализовывать весь backlog одним большим изменением.

## Первый запуск AI-разработчика

Первая ограниченная порция: **LUM-002, затем LUM-003**. Для них не нужен ответ
о реальной инфраструктуре студии. LUM-001 может оставаться partial: составить
каталог неизвестных параметров и использовать явно помеченные fixtures до ответа.
Не угадывать подключения и не считать LUM-001 завершённой без реальных данных.

Для LUM-002 проверить зависимости и выполнить доступные команды:

| Каталог | Команда | Назначение |
|---|---|---|
| `server/` | `go test ./...` | Существующие Go-тесты |
| `web/` | `npm run typecheck` | Проверка TypeScript |
| `web/` | `npm run build` | Сборка web |

Версии среды брать из проекта. Установку зависимостей выполнять существующим
менеджером и lockfile, когда он есть. Не использовать общий `make test`: он
захватывает Rust/Flutter, которые сейчас вне области работ. Отсутствующий инструмент
или недоступный registry записывать как ограничение, а не как успешную проверку.

Для LUM-003 сначала воспроизвести сброс draft при обновлении revision в
`web/src/pages/NotePage.tsx`. Исправить base revision, обработку обновления и
конфликта; добавить минимальную UI-проверку именно этого поведения. Если test
runner отсутствует, добавить один необходимый runner без массовой перестройки
frontend. Не менять одновременно весь редактор на CodeMirror.

Приёмка первой порции: несохранённый текст остаётся после SSE/refetch, конфликт
показывается без потери текста, unrelated API ошибки не называются конфликтом,
typecheck/build пройдены либо точно описан внешний blocker. Изменения desktop — ноль.

## Цикл одной задачи

1. Проверить git diff/status, прочитать область кода; сохранить чужие изменения.
2. Выбрать одну готовую задачу или небольшой связный набор с выполненными зависимостями.
3. Записать в progress статус `in_progress`, краткий scope и критерии результата.
4. Для новой сущности определить API/schema и модель доступа; для хранения —
   миграцию/rollback. Не генерировать UI под несуществующий контракт молча.
5. Реализовать минимальный полный сценарий и проверить его meaningful tests.
6. Обновить документацию и progress: файлы, команды, фактические результаты,
   ограничения, оставшиеся пункты приёмки и следующий task ID.
7. Задача становится `done` только после приёмки. Заглушка, mock UI и зелёная
   компиляция не доказывают работу реального коннектора, изоляции или восстановления.

Если зависимость блокирует реализацию, сделать доступную независимую работу и
зафиксировать точную причину. Новая архитектурная необходимость оформляется кратким
ADR и правкой зависимых задач. Не ставить большой незаявленный refactor вместо задачи.

## Стартовый запрос, который можно передать модели

```text
Работай в репозитории Lumen. Прочитай AGENTS.md, docs/plans/PRODUCT_DIRECTION.md,
docs/plans/IMPLEMENTATION_GUIDE.md, docs/plans/BACKLOG.md и docs/plans/PROGRESS.md.
Цель продукта — AI-центр управления студией с проектами, агентами, знаниями и
действиями в существующих сервисах. Сохрани Go/React, Markdown и текущий API;
desktop/Flutter/Rust пока не меняй.

Начни с LUM-002, затем реализуй LUM-003. Проверяй фактическое состояние кода,
сохраняй имеющиеся изменения. Добавь проверку потери draft при внешнем обновлении,
исправь поведение, выполни относящиеся к задаче проверки. Не ограничивайся планом.
Не разворачивай OpenSearch, не подключай боевые сервисы и не реализуй весь backlog.
Обнови PROGRESS.md с доказательствами, ограничениями и следующим шагом.
Если эта порция уже сделана, выбери следующую готовую задачу по зависимостям
и порядку срезов. В конце сообщи, что реализовано, как проверено и что осталось.
```

Этот запрос ограничивает первую итерацию; для продолжения достаточно поручить
следующий срез. Наличие плана не гарантирует корректность генерируемого кода:
проверки, review миграций и демонстрации сценариев остаются частью каждой поставки.
