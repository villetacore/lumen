# План взаимодействия с существующими сервисами

Статус: предложение. Основной приоритет — углубить имеющиеся интеграции.

## Сначала инвентаризация

Для каждого реально используемого сервиса заполнить:

| Поле | Что зафиксировать |
|---|---|
| Сервис и владелец | Название, instance URL, ответственный, размещение |
| Сценарий | Что читаем, что изменяем и зачем пользователю Lumen |
| Интерфейс | API, webhook, MCP, export; версия и ограничения |
| Доступ | Личная или сервисная учётная запись, scopes, группы и ACL объектов |
| Нагрузка | Объекты, изменения/сутки, лимиты запросов, допустимое отставание |
| Эксплуатация | Разрешённые сети, timeout, резервное чтение, отзыв доступа |

Не подключать Jira, почту или чат только ради количества логотипов. Выбирать
следующий коннектор по конкретному сквозному сценарию. Если в окружении есть n8n
или другой оркестратор, использовать его для сложных workflow через проверяемые
webhooks/actions, не строить его аналог внутри Lumen.

## Матрица первых подключений

| Система | Сейчас в коде | Следующий шаг | Граница ответственности |
|---|---|---|---|
| GitHub/Gitea/Forgejo | Импорт issues/PR | Карточка, связанный проект, webhook и явное закрытие issue | Статус и права определяет трекер; совместимость форков проверять отдельно |
| Nextcloud Notes | Импорт заметок | Корректное обновление внешнего body, версии и удаления | Внешний текст отдельно от личных дополнений |
| CalDAV | Чтение встреч | Проверенный read-model, затем создание/перенос с ETag | Календарь определяет recurrence и конфликт версии |
| ICS | Чтение | Устойчивый snapshot и отображение freshness | Остаётся read-only; секретная URL-подписка считается credential |
| Keycloak/OIDC | Вход | Группы → workspace-права, отзыв доступа | Не является универсальным токеном всех сервисов |
| Bitwarden/KeePass | Secret refs и чтение паролей | Сохранить изоляцию секретов от индекса и AI | Не публиковать reveal через MCP и retrieval |
| Документация в Git/другом сервисе | Отдельного коннектора знаний нет | Добавить один выбранный источник с provenance и ACL | Не импортировать произвольные сайты без заданной области |

Первое внешнее действие — `close_issue` для одного выбранного экземпляра GitHub
**или** Gitea. Другие системы и типы записи добавляются после приёмки этого пути.

## Контракт коннектора

Разделить capabilities: `discover`, `read`, `list_changes`, `subscribe`,
`preview_action`, `execute_action`, `reconcile_action`. Реализация заявляет только
поддерживаемое; ICS не обязан реализовывать запись. UI строит список действий
по capabilities и правам пользователя.

Результат чтения содержит stable external ID, тип, canonical URL, версию/ETag,
время обновления, удаление, ACL и provenance. Отдельно указать: это полный snapshot
или delta; для delta нельзя удалять все объекты, не пришедшие в странице ответа.

Вход коннектора содержит scope подключения, deadline, cursor и resolver секретов.
Коннектор не пишет Markdown и не решает, кому доступен объект в Lumen. Нормализация,
применение проекций и проверка прав относятся к прикладному слою.

Действие содержит типизированную схему аргументов, target, remote version,
idempotency key и ожидаемый эффект. Произвольный URL, shell-команда или сырой HTTP
запрос не являются пользовательским действием.

## Обновление и конфликты

- Polling оставить как механизм полной сверки; webhooks уменьшают задержку,
  но не заменяют reconciliation. Проверять подпись, timestamp и повтор delivery.
- Cursor сохранять только после устойчивого применения страницы. После ошибки
  применять её снова идемпотентно. На первом запуске без snapshot игнорировать
  сохранённый ETag и загружать полный набор.
- Разделить внешнюю проекцию и локальные дополнения. Для legacy-файлов, где граница
  текста неоднозначна, показывать diff и сохранять копию, не угадывать авторство.
- Идентификаторы включают connection/instance. При миграции `^block-id` сохранить
  таблицу старых ссылок и не переименовывать существующие задачи молча.
- Удаление/отзыв доступа скрывает объект из выдачи, RAG и кэшей; личная заметка
  сохраняется по своей политике, но недоступный внешний текст из неё не раздаётся.
- Источник владеет своими полями. Локальная галочка не должна незаметно становиться
  командой закрыть issue; внешняя запись — отдельное действие с результатом.

## Жизненный цикл действия

`draft → awaiting_approval → queued → running → succeeded / failed / unknown`.
Дополнительно: `expired`, `cancelled`, `conflict`. Подтверждение нужно по политике
операции; обычное явное нажатие «Закрыть issue» с точным preview может быть самим
подтверждением, без второго одинакового диалога.

1. Пользователь или помощник готовит preview: сервис, объект, текущая версия,
   изменение, инициатор и используемое подключение.
2. Сервер сохраняет подтверждение, привязанное к хэшу этих параметров и сроку.
   Изменённый target или payload требует нового preview.
3. Перед исполнением повторно проверяются права и актуальность версии. Конфликт
   требует нового решения; помощник не может сам себе выдать разрешение.
4. Операция фиксируется в outbox, исполняется и получает receipt с remote ID.
   При таймауте после отправки — `unknown`, затем проверка результата в источнике.
5. UI и MCP получают один action ID. Повторный клик возвращает ту же операцию.
   Обновление карточки подтверждается чтением результата из сервиса.

## Доступ к внутренним сервисам

Сохранить существующую защиту от SSRF. Вместо широкого `allow_private` для новых
подключений — администраторский allowlist конкретных hosts/ports и, при нужде,
подсетей. Проверять DNS/redirect на каждом соединении. Передавать credential
только разрешённому origin; служебные metadata-адреса запрещены.

OAuth grants разделять по пользователю и подключению. Service account допускается
с явной политикой публикации; если источник не отдаёт ACL и их нельзя проверить,
его данные доступны владельцу подключения, а не всему workspace. Диагностика и
пробные подключения не должны раскрывать credential в ошибках.
