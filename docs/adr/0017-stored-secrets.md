# ADR-0017. Токены из форм хранятся зашифрованными

**Статус:** принято · 2026-11-04. Уточняет [ADR-0007](0007-secret-references.md): ссылки на
секреты остаются, но больше не единственный способ.

## Контекст
Поля секретов принимали только ссылки (`env:…`). Человек вполне логично вставил в поле сам
ключ. Значение без префикса разобралось как путь к файлу, попало в текст ошибки на экране и
осталось открытым текстом в `.lumen/passwords.yaml` внутри vault, а значит, и в его копиях.
К тому же ссылка `env:` на боевом сервере требует правки манифестов ради каждого токена.

## Решение
Вставленное значение шифруется (AES-256-GCM) и хранится в таблице `stored_secrets` операционной
БД, а в настройки записывается только `stored:<id>`. Значения обратно в интерфейс не отдаются.
Ссылки (`env:`, `file:`, `command:`, `bitwarden:`, `keepass:`, абсолютный путь) работают как раньше.

Ключ — `LUMEN_SECRETS_KEY`, иначе файл `secrets.key` (0600), созданный рядом с БД в `--state`.
Дамп БД без ключа ничего не открывает. **Копия операционной БД без ключа секретов не вернёт:**
токены придётся ввести заново, больше ничего не пострадает.

При запуске старые открытые значения в настройках переносятся и стираются из файла. Копии vault,
сделанные раньше, менять некому: такие секреты нужно перевыпускать. Если хранилище недоступно,
значение отклоняется, а не записывается в файл.

## Последствия
**Плюсы.** Токен вводится в форме и не требует правки манифестов; файлы vault чисты от секретов.

**Минусы.** Ключ и БД находятся на одном сервере: от того, кто получил весь сервер, это не защищает,
только от утечки файлов vault, дампов и бэкапов БД. Для усиления задайте `LUMEN_SECRETS_KEY`
из внешнего хранилища. При смене ключа токены нужно ввести заново.
