# ADR-0012. Политика доступа: роли пространства и проекты с участниками

**Статус:** принято · 2026-11-02 (LUM-012)

## Контекст
До сих пор вошедший пользователь видел и менял весь vault, включая пароли и
интеграции. Командная работа (срез T2) требует закрытых проектов, ролей
«читатель/участник/администратор» и одинаковых запретов для HTTP, поиска,
SSE, сервисов и будущих MCP/агентов (AGENTS.md: доступ определяется кодом).

## Решение
1. **Субъект** (`policy.Principal`) кладётся в контекст запроса всегда:
   OIDC — из claims (`preferred_username`, группы, роли); статический токен и
   локальный режим — служебный субъект с ролью администратора. Нет субъекта в
   контексте — доступ закрыт (fail closed).

2. **Роли пространства**: `admin`, `member`, `viewer`. Для OIDC задаются
   `--admin-roles` и `--viewer-roles` (роли клиента/realm или группы Keycloak).
   Совместимость: если `--admin-roles` не задан, каждый допущенный пользователь —
   администратор, как было до этого решения. Иначе: совпадение с admin-ролями —
   `admin`, с viewer-ролями — `viewer`, остальные допущенные — `member`.

3. **Проекты**: проект трекера без участников — открытый, в нём действует роль
   пространства. Проект с хотя бы одной записью участника — закрытый: доступ
   только у участников (`user:<username>` или `group:<группа>`, роль
   `viewer|member|admin`) и у администраторов пространства. Роль в проекте
   может быть выше роли пространства (читатель пространства — участник проекта).

4. **Принадлежность материала проекту** вычисляется из vault, без копии в БД:
   тикет и спринт — по полю `project`; заметка проекта — по `key`; любой файл в
   папке проекта `<папка заметки>/<KEY>/…`; документ с `parent: note:…` или
   `task:…` — по родителю (до 5 уровней). Остальное — материалы пространства.

5. **Хранение участников** — операционная БД (ADR-0011), таблица
   `project_members`; не во frontmatter: иначе любой, кто может править заметку
   проекта, мог бы выдать себе доступ.

6. **Применение**:
   - чтение — обёртка `policy.Scoped` над `index.Store`: невидимое отфильтровано
     из списков, поиска, тегов, календаря, обратных ссылок и статистики, а
     прямой запрос отвечает «не найдено» (существование не раскрывается);
   - запись — проверки в сервисах (`Notes`, `Tasks`, `Issues`): нужна роль
     `member`; создание файла проверяется по пути и родителю;
   - SSE — событие уходит подписчику, только если он видит путь;
   - интеграции, хранилища паролей и переиндексация — только `admin`;
   - участников проекта меняют администратор пространства или проекта.
   Фоновые процессы (индексатор, интеграции) работают с исходным хранилищем.

## Последствия
**Плюсы:** одно место решений для всех каналов; закрытые проекты без смены
формата файлов; прежние установки без `--admin-roles` ведут себя как раньше.
**Минусы:** доступ ограничивает Lumen, а не файловая система: кто имеет доступ к
vault на диске, Obsidian или Nextcloud, видит всё. Принадлежность вычисляется
при каждом запросе (для пилота достаточно, индекс — при росте объёма).
Добавление первого участника закрывает проект для остальных — интерфейс
должен об этом предупреждать.

## Альтернативы
- **Права во frontmatter проекта.** Самоповышение прав через правку заметки. Отклонено.
- **Отдельные vault на проект.** Ломает ссылки и общий поиск. Отклонено.
- **Проверки в HTTP-обработчиках.** Расходятся с MCP и агентами. Отклонено.
