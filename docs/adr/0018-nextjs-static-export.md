# ADR-0018. Веб-клиент на Next.js, статический экспорт

**Статус:** принято · 2026-11-04

## Контекст
Владелец попросил перевести `web/` с Vite на Next.js. При этом действует
[ADR-0006](0006-single-binary.md): клиент вшит в `lumend`, образ distroless без
Node, отдельного процесса с фронтендом нет. Данные клиента приватные и приходят
из API после входа, поэтому серверный рендер почти ничего не даёт.

## Решение
Next.js работает в режиме `output: "export"`. Сборка кладёт статику в `web/dist`,
откуда её, как и раньше, забирают `make app`, `scripts/build.ps1` и Dockerfile.

Экспорт содержит одну страницу: `src/app/[[...slug]]/page.tsx` рендерит приложение
только в браузере (`ssr: false`). `lumend` отдаёт `index.html` на любой глубокий
адрес, дальше маршрутизирует React Router.

React Router остаётся, файловая маршрутизация Next не используется:

- адреса `/tracker/:key`, `/issue/:key`, `/note/*` заранее неизвестны, а экспорт
  требует перечислить их при сборке;
- защита черновика построена на `useBlocker`, аналога в `next/navigation` нет.

Каталог `src/pages` переименован в `src/screens`: это имя зарезервировано за
Pages Router. Next нужен только для сборки и dev-сервера. Vite остаётся
dev-зависимостью как основа Vitest.

Dev-сервер проксирует `/api`, `/auth`, `/healthz` через `rewrites`. Токен
`make dev-prod` добавляет `src/proxy.dev.ts`, который загружается только в `next dev`
(расширение `dev.ts` есть в `pageExtensions` только в этой фазе).

## Последствия
**Плюсы:** один бинарник, API и развёртывание не меняются, Node в рантайме не нужен.
**Минусы:** SSR, route handlers, server actions, `next/image` с оптимизацией и
серверный proxy недоступны; большая часть возможностей Next не используется, а сборка
зависит от более тяжёлого пакета. Первый экран по-прежнему пуст до загрузки JS.

## Миграция
Обратная совместимость API и данных полная. `lumend` кэширует навсегда
`_next/static/` вместо `assets/`. Если понадобится SSR, это отдельное решение: оно
отменяет ADR-0006 и добавляет Node в образ и развёртывание.
