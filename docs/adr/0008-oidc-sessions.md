# ADR-0008. Вход через OIDC: код авторизации на сервере, сессия в cookie

**Статус:** принято · 2026-09-08

## Контекст
Сервер разворачивается рядом с другими сервисами за Keycloak. Нужен вход,
который встраивается в существующий SSO. Варианты:

1. PKCE прямо в SPA, токен живёт в JavaScript.
2. Код авторизации на сервере, браузер носит HttpOnly-cookie.
3. Довериться обратному прокси (oauth2-proxy) и читать заголовки.
4. Свои пользователи и пароли.

## Решение
Вариант 2: authorization code + PKCE выполняет сервер, браузеру достаётся только
идентификатор сессии в HttpOnly-cookie. Плюс приём `Authorization: Bearer` с
токеном того же realm — для десктопа, скриптов и соседних сервисов.

Проверка токенов сделана на стандартной библиотеке: RS256 через `crypto/rsa` и
разбор JWKS. Внешняя библиотека ради трёхсот строк не нужна.

## Последствия
**Плюсы**
- Токен недоступен из JavaScript: XSS не уносит доступ к Keycloak.
- Один механизм закрывает и браузер, и машинных клиентов.
- Работает и с публичным клиентом (PKCE), и с конфиденциальным.
- Ролевая проверка на месте: `--oidc-roles` понимает и роли, и группы.

**Минусы**
- Сессии лежат в памяти: перезапуск сервера разлогинивает всех.
- Refresh-токен пока не используется, срок сессии задаётся `--session-ttl`.
- Discovery при старте — если Keycloak недоступен, Lumen не поднимется с SSO.

**Почему не остальные варианты**
- (1) Токен в JS — лишний риск ради экономии двух эндпоинтов.
- (3) Прокси удобен, но привязывает к конкретному развёртыванию и не помогает
  десктопу, который ходит напрямую.
- (4) Свои пароли там, где уже есть SSO, — ровно то, чего просили избежать.

## Проверки, которые обязаны остаться
`alg: none` и HMAC отвергаются до проверки подписи; `iss` сверяется с realm;
`aud` **или** `azp` должен совпасть с client id — Keycloak заполняет их
по-разному для id- и access-токенов. На всё это есть тесты с поддельным Keycloak.
