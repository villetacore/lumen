# ADR-0010. Тикет — отдельный Markdown-файл

**Статус:** принято · 2026-11-02 (LUM-060)

## Контекст
Владелец хочет трекер уровня Jira: workflow-колонки, исполнители, спринты,
комментарии, история, связи. Текущая задача Lumen — строка `- [ ]` с инлайн-полями
(`spec/FORMAT.md` §2): в ней нет места для описания, комментариев и множества полей.

## Решение
Тикет — файл `<папка проекта>/<KEY>/issues/<KEY>-<N>.md` с `type: issue` во frontmatter
(поля — в [`spec/FORMAT.md` §7](../../spec/FORMAT.md#7-трекер-проект-тикет-спринт)). Проект — заметка `type: project`
с полем `key` и workflow, спринт — `sprints/<id>.md`. Комментарии — разделы
`### <время> · <user> ^c-<id>` под `## Комментарии`. Порядок на доске — дробный ранг в
поле `rank`. Чекбоксы внутри тикета остаются обычными задачами §2.

История изменений, пользователи и членство хранятся в операционном хранилище
(LUM-010) и входят в бэкап; они не являются контентом и не дублируются во frontmatter.

## Последствия
**Плюсы:** тикет читается и правится в Obsidian/git; ссылка `[[WEB-12]]` устойчива к
переименованию; Markdown остаётся источником правды (ADR-0001).
**Минусы:** много мелких файлов; запись комментария — read-modify-write файла
(сериализуется существующим `vaultWrites`); отчёты зависят от журнала в БД.
**Уточнение ADR-0004:** семантика тикета реализуется только в Go; Rust/desktop
читает тикет как обычную заметку. Golden-фикстуры тикета проверяет Go.

## Альтернативы
- **Расширить строку-задачу полями.** Нет комментариев, описания, истории. Отклонено владельцем.
- **Тикеты в БД.** Противоречит ADR-0001.
- **Комментарии отдельными файлами.** Меньше конфликтов записи, но хуже читается; пересмотреть, если конфликты станут частыми.
