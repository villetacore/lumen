# ADR-0011. Операционное состояние в SQLite рядом с vault

**Статус:** принято · 2026-11-02 (LUM-006, реализация — LUM-010)

**Уточнение 2026-11-04:** операционная БД может находиться в PostgreSQL, см. [ADR-0015](0015-postgres-redis.md). SQLite остаётся вариантом по умолчанию.

## Контекст
ADR-0001 делает Markdown источником правды и разрешает только удаляемые индексы.
Трек «Команда» (LUM-066…068) и дальнейшие задачи требуют данных, которых нет в
файлах и которые нельзя восстановить из них: пользователи и группы из OIDC,
членство в проектах, история изменений тикетов (по ней строится burndown),
уведомления, позже — задания, внешние действия, права и связи (LUM-012/013/023).
Сейчас такое состояние разбросано: `.lumen/*.yaml` (конфигурация интеграций и
хранилищ паролей) и `.lumen/cache/integrations-state.json` внутри vault, индекс
живёт в памяти.

## Решение
1. **Три класса данных** с разными правилами восстановления:

   | Класс | Где | Потеря |
   |---|---|---|
   | Контент: заметки, задачи, тикеты, спринты, страницы, комментарии | Markdown в vault (ADR-0001) | Недопустима; бэкап vault |
   | Операционное состояние: пользователи, членство, история, уведомления, задания, действия | SQLite `lumen.db` в каталоге состояния | Недопустима; отдельный обязательный бэкап |
   | Производное: индекс, поиск, агрегаты | Память / удаляемые файлы | Допустима; пересобирается из vault |

   Правило отнесения: если данные можно получить заново из vault или внешнего
   сервиса — это производное; если нет — операционное. Контент никогда не
   копируется в БД как источник правды; в БД допустимы ссылки на него (ключ
   тикета, путь) и значения полей в истории изменений.

2. **Каталог состояния вне vault**: флаг `--state` / `LUMEN_STATE`. По умолчанию —
   `lumen-state` рядом с папкой vault (`/var/lib/lumen/vault` →
   `/var/lib/lumen/lumen-state`), в Docker — том `/state`. БД не синхронизируется
   вместе с vault (Obsidian, git, Nextcloud) и не индексируется. Существующие
   `.lumen/*.yaml` не переносятся этим ADR: это конфигурация vault, их перенос —
   отдельное решение при необходимости.

3. **SQLite через `modernc.org/sqlite`** (чистый Go): сборка остаётся
   `CGO_ENABLED=0` и одним бинарником (ADR-0006). Режим WAL, `foreign_keys=on`,
   `busy_timeout`, одно соединение на запись. Один процесс на каталог состояния
   (файл-блокировка `lumen.lock`): второй `lumend` с тем же `--state` не стартует.

4. **Миграции** — пронумерованные SQL-файлы, встроенные в бинарник; таблица
   `schema_migrations(version, name, applied_at)`. Каждая миграция применяется в
   своей транзакции. Перед применением новых миграций к непустой БД автоматически
   делается копия `backups/pre-<версия>-<время>.db`. Таблицы добавляют задачи,
   которым они нужны (066 — пользователи, 068 — история, 013 — задания и т. д.),
   а не заранее «на будущее».

5. **Откат версии**: бинарник, который видит в БД миграцию новее известных ему,
   отказывается стартовать с понятной ошибкой. Откат = старый бинарник +
   восстановление копии `pre-<версия>` (или своего бэкапа). Миграции вперёд-только,
   down-миграций нет.

6. **Бэкап и восстановление**: `lumend state backup <файл>` делает согласованную
   копию работающей БД (`VACUUM INTO`); `lumend state restore <файл>` — только при
   остановленном сервере (проверяется блокировкой), с проверкой целостности
   (`PRAGMA integrity_check`) и сохранением текущей БД в `backups/`. Восстановление
   vault и БД делается из копий одного момента; при расхождении vault главнее:
   история может ссылаться на удалённые тикеты, но не наоборот.

7. **Шифрованный vault** (ADR-0005): значения, несущие контент (например, старое и
   новое значение поля в истории), записываются через тот же `vault.Codec`
   (`store.Seal`/`Open`), а структура (ключи, время, автор, имена полей) — открыто.
   Без кодека значения хранятся как есть.

8. **Граница пилота**: один сервер, один процесс, одна БД; несколько
   пользователей — через OIDC после тестов изоляции (LUM-012/057). PostgreSQL и
   отдельные воркеры — только при доказанной необходимости, тем же интерфейсом
   хранилища.

## Последствия
**Плюсы:** история и команда возможны без нарушения ADR-0001; бэкап и откат
описаны до появления первых данных; один бинарник сохраняется.
**Минусы:** второй обязательный бэкап; vault и БД могут разойтись во времени;
pure-Go SQLite медленнее cgo-версии (для пилота несущественно).
**Эксплуатация:** Docker получает том `/state`; существующие развёртывания должны
добавить постоянный каталог для `LUMEN_STATE`, иначе состояние теряется при
пересоздании контейнера (сейчас там ещё нет незаменимых данных).

## Альтернативы
- **Хранить состояние в `.lumen/` внутри vault.** Попадает в синхронизацию vault
  (Obsidian Sync, git, Nextcloud), даёт конфликты бинарного файла. Отклонено.
- **История в front matter или файлах-журналах в vault.** Раздувает файлы, ломает
  чистые diff, конфликтует при одновременной правке. Отклонено.
- **PostgreSQL сразу.** Лишний сервис для однопроцессного пилота. Отложено.
- **`mattn/go-sqlite3` (cgo).** Ломает статическую сборку. Отклонено.
