# ADR-0013. MCP-сервер внутри lumend

**Статус:** принято · 2026-11-02 (LUM-040; записи — по запросу владельца, ранее LUM-041)

## Контекст
Владелец хочет подключать к Lumen AI-клиенты (Claude Desktop/Code, Cursor и
другие) по Model Context Protocol: сначала чтение, затем записи с
подтверждением. AGENTS.md требует, чтобы MCP использовал общие
service/policy/actions и чтобы доступ определял код, а не промпт.

## Решение
1. **Где.** Эндпоинт `/mcp` в том же `lumend` (ADR-0006), транспорт Streamable
   HTTP, официальный Go SDK `github.com/modelcontextprotocol/go-sdk` v1.8.0
   (версии протокола 2024-11-05 … 2026-07-28 по согласованию с клиентом).
2. **Без сессий (stateless).** Каждый POST обрабатывается сам по себе; сервер не
   держит MCP-сессий и не шлёт запросов клиенту. Субъект берётся из этого же
   HTTP-запроса, поэтому подмена чужой сессии невозможна по построению.
3. **Вход.** Те же способы, что у API (ADR-0008/0012): Bearer-токен Keycloak или
   статический токен; в локальном режиме без авторизации — локальный субъект.
   **Cookie браузерной сессии для MCP не принимаются**: только заголовок
   `Authorization`, иначе страница другого сайта могла бы вызывать инструменты
   от имени вошедшего. Защита SDK от DNS rebinding для localhost включена.
4. **Права.** Инструменты вызывают те же сервисы и обёртку индекса, что и
   HTTP API (`policy.Scoped`, `Check*`): закрытые проекты не видны, запись без
   роли запрещена. Пароли, интеграции и администрирование через MCP не
   доступны вообще.
5. **Чтение** — инструменты с `readOnlyHint`: кто я, поиск, заметка, проекты,
   тикеты (фильтры, «мои»), тикет целиком, история, спринты. Ответы — JSON со
   схемой; длинные тексты обрезаются с пометкой.
6. **Записи — только с подтверждением человека.** Инструмент записи не меняет
   данные, а создаёт *предложение*: точное изменение и предпросмотр. Применяет
   его человек в веб-интерфейсе Lumen (не модель и не MCP-клиент). Предложение
   привязано к автору, аргументам и версии тикета; устаревает (тикет изменился)
   и истекает; применяется один раз; повтор с тем же `request_id` возвращает
   то же предложение. Применение идёт через обычные сервисы с правами
   подтвердившего — он должен быть тем же пользователем.

## Последствия
**Плюсы:** один бинарник, одни права для веба, API и агентов; модель не может
сама провести изменение.
**Минусы:** stateless не даёт уведомлений от сервера клиенту и elicitation;
подтверждение требует открыть Lumen.

## Альтернативы
- **Отдельный процесс MCP (stdio) поверх HTTP API.** Второй бинарник и второй
  слой авторизации. Отложено: при необходимости — тонкий прокси.
- **Подтверждение через elicitation в клиенте.** Поддерживается не всеми
  клиентами и требует сессий; кроме того, подтверждение остаётся внутри
  контура, которым управляет модель. Отклонено для записей.
- **Прямые записи с `destructiveHint`.** Доверие клиенту в вопросе
  подтверждения. Отклонено.
